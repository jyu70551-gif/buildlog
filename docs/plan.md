# BuildLog MVP 개발 계획

## 1. 계획의 목적

이 문서는 `spec.md`에 정한 기능을 어떤 순서로 개발할지 설명합니다.

처음 개발하는 과정에서 한 번에 너무 많은 내용을 다루지 않도록 작업을 작은 Phase로 나눕니다. 한 번의 작업에서는 Phase 하나만 진행하고, 확인 기준을 모두 통과한 뒤 다음 Phase로 넘어갑니다.

## 2. 개발 원칙

- `spec.md`에 없는 기능은 추가하지 않습니다.
- 각 Phase가 끝날 때 자동 테스트와 직접 화면 확인을 함께 수행합니다.
- 확인에 실패하면 다음 Phase로 넘어가지 않고 현재 Phase만 수정합니다.
- 화면(React)에서 버튼을 숨기는 것만으로 권한을 처리하지 않습니다. 서버(FastAPI)에서도 사용 권한을 검사합니다.
- 글자 수와 필수 입력 같은 규칙도 화면의 검사에만 맡기지 않고 서버에서 반드시 검사합니다.
- 비밀번호와 비밀 설정값을 코드에 저장하거나 화면에 보여주지 않습니다.
- 개발과 자동 테스트는 SQLite3로 하고, 실제 서비스는 Supabase(PostgreSQL)를 씁니다. 두 곳에서 같은 결과가 나오도록 SQLite 전용 기능은 쓰지 않습니다.
- Supabase는 데이터베이스로만 사용합니다. 회원가입과 로그인은 서버가 직접 처리합니다.
- 실제 SQLite 데이터 파일, `.env`, `.venv`, `node_modules`, 로그와 생성 파일은 Git 기록 대상에서 제외합니다.
- Git 초기화와 커밋은 별도 요청이 있기 전까지 수행하지 않습니다.
- FastAPI와 React의 기본 기능을 우선 사용하고 꼭 필요하지 않은 외부 패키지는 추가하지 않습니다.

## 3. 사용할 기술

| 구분 | 기술 | 역할 |
| --- | --- | --- |
| 화면 | React (Vite로 시작), React Router | 사용자가 보고 누르는 화면, 화면 이동 |
| 서버 | Python, FastAPI | 화면의 요청을 받아 규칙과 권한을 검사하고 데이터를 저장·조회 |
| 데이터 접근 | SQLAlchemy, Alembic | 데이터 저장 구조를 코드로 정의하고, 구조 변경 기록(마이그레이션) 관리 |
| 개발·테스트 데이터베이스 | SQLite3 | 파일 하나로 빠르게 개발하고 자동 테스트 |
| 실제 서비스 데이터베이스 | Supabase (PostgreSQL) | 인터넷에서 어디서든 같은 기록을 볼 수 있는 저장소 |
| 테스트 | pytest, httpx (서버) / Vitest, Testing Library (화면) | 자동 테스트 |

- 위 표의 세부 도구(SQLAlchemy, Alembic, React Router 등)는 이 계획의 추천이며, Phase 0에서 호환되는 안정 버전과 함께 확정합니다.
- 서버와 화면은 따로 실행되고, 화면이 서버에 요청해서 데이터를 주고받습니다.

## 4. 예정된 프로젝트 구조

실제 개발을 시작하면 다음과 같이 역할을 나눕니다. 이름은 개발 중 임의로 바꾸지 않습니다.

```text
buildlog/
├─ backend/
│  ├─ requirements.txt
│  ├─ .env.example
│  ├─ alembic/            # 데이터 구조 변경 기록(마이그레이션)
│  ├─ app/
│  │  ├─ main.py          # 서버 시작점과 공통 설정
│  │  ├─ config.py        # .env 설정 읽기
│  │  ├─ database.py      # 데이터베이스 연결
│  │  ├─ security.py      # 비밀번호 처리, 로그인 확인
│  │  ├─ accounts/        # 회원가입, 로그인, 닉네임
│  │  ├─ records/         # 공부 기록, 할 일, 오류 기록
│  │  └─ community/       # 댓글, 좋아요, 신고
│  └─ tests/              # 서버 자동 테스트
├─ frontend/
│  ├─ package.json
│  ├─ .env.example
│  └─ src/
│     ├─ api/             # 서버에 요청하는 코드
│     ├─ components/      # 공통 화면 조각
│     ├─ pages/           # 사용자가 보는 화면
│     └─ styles/          # CSS
├─ database/
│  └─ buildlog.sqlite3    # 개발·테스트 데이터 파일, Git 제외
└─ docs/                  # 요구사항, 동작 설명서, 개발 문서
```

- `accounts`, `records`, `community` 안에는 각각 데이터 구조(models), 입력 검사(schemas), 요청 처리(router)를 둡니다.
- 개발 중 서버 주소는 `http://localhost:8000`, 화면 주소는 `http://localhost:5173`을 예정으로 합니다.

## 5. 전체 개발 순서

| Phase | 만드는 결과 | 다음 Phase로 넘어가기 위한 핵심 조건 |
| --- | --- | --- |
| 0 | 개발 기준과 환경 확인 | 문서와 개발 환경에 충돌이 없음 |
| 1 | 실행 가능한 서버·화면 뼈대 | 빈 서버와 빈 화면이 정상 실행되고 서로 연결됨 |
| 2 | 사용자 데이터 구조와 데이터베이스 시작점 | 첫 마이그레이션과 사용자 테스트 통과 |
| 3 | 회원가입·로그인·닉네임 | 회원 기능과 접근 제한 테스트 통과 |
| 4 | 세 가지 기록의 데이터 구조 | 저장·재실행·제약 조건 테스트 통과 |
| 5 | 공부 기록 전체 흐름 | 공부 기록 기능만 단독으로 완성 |
| 6 | 할 일 전체 흐름 | 할 일 기능만 단독으로 완성 |
| 7 | 오류 기록 전체 흐름 | 오류 기록 기능만 단독으로 완성 |
| 8 | 공개 기록·공개 범위·공개 검색 | 비공개 유출 없이 공개 기능 동작 |
| 9 | 댓글 | 댓글 조건과 권한 테스트 통과 |
| 10 | 좋아요 | 중복 방지와 취소 테스트 통과 |
| 11 | 신고와 운영자 확인 | 신고 저장·중복 방지·운영자 권한 확인 |
| 12 | 반응형 화면과 공통 오류 처리 | 360px 이상 화면과 지정 브라우저 확인 |
| 13 | 전체 통합 확인과 실행 문서 | `spec.md`의 완료 조건 전체 통과 |
| 14 | Supabase 연결과 인터넷에 올리기 | Supabase에서도 같은 결과, 폰과 다른 컴퓨터에서 접속 확인 |

Phase 14는 Supabase를 쓰기로 한 결정을 반영해 새로 추가한 단계입니다. 올릴 곳(호스팅)은 아직 정하지 않았습니다.

## 6. Phase별 상세 계획

### Phase 0. 개발 시작 전 기준 확인

#### 목표

코드를 만들기 전에 문서, 도구, 실행 환경을 확인합니다.

#### 작업

1. `PRD.md`, `spec.md`, `plan.md`의 기능 범위와 기술 구성이 서로 맞는지 확인합니다.
2. 첫 버전에서 만들지 않을 기능을 다시 확인합니다.
   - 이메일 확인
   - 비밀번호 찾기
   - 할 일 마감일과 중요도
   - 내 할 일 검색
   - 댓글 답글
3. 사용할 Python, FastAPI, Node.js, React의 서로 호환되는 안정 버전을 확인합니다.
4. SQLite가 Python 환경에서 사용 가능한지 확인합니다.
5. 서버·화면 개발 주소, 데이터베이스 파일 위치, 환경 변수 이름을 정리합니다.
6. 서버와 화면의 테스트 명령과 실행 명령을 문서에 기록할 준비를 합니다.

#### 예상 변경 파일

- `docs/plan.md`
- 필요 시 실행 환경을 설명할 `docs/setup.md`
- 코드와 패키지는 아직 변경하지 않음

#### 확인 방법

- 세 문서를 읽었을 때 기능 범위와 기술 구성이 충돌하지 않는지 확인합니다.
- Python, Node.js 실행 여부와 버전을 읽기 전용 명령으로 확인합니다.
- 아직 패키지를 설치하거나 데이터베이스를 만들지 않았는지 확인합니다.

#### 확인된 현재 상태

- Python 3.12.10(`py -3.12`)과 3.14.6(`python`)이 있고, 추천은 3.12입니다.
- Node.js v24.22.1, npm 11.19.1, Git 2.56.0이 있습니다.
- Python의 SQLite 모듈은 사용 가능합니다.
- 프로젝트 맨 위에 임시로 만든 빈 `.venv`가 있습니다. Phase 1에서 지우고 `backend/.venv`를 새로 만듭니다.

#### 완료 조건

- 개발 환경과 기능 범위에 막히는 항목이 없어야 합니다.
- 확인 결과를 공유하고 다음 Phase 진행 여부를 확인합니다.

### Phase 1. 서버·화면 뼈대 만들기

#### 목표

기능 없이도 서버와 화면이 실행되고, 화면이 서버와 연결된 것을 볼 수 있게 합니다.

#### 작업

1. 임시로 만든 맨 위의 빈 `.venv`를 지우고 `backend/.venv`에 가상환경을 준비합니다.
2. FastAPI, 서버 실행 도구(Uvicorn), 설정 읽기 도구, 테스트 도구(pytest, httpx)만 먼저 설치하고 정확한 버전을 `backend/requirements.txt`에 기록합니다.
3. `backend/app`에 서버를 만들고 상태 확인 주소(`/api/health`) 하나만 연결합니다.
4. `frontend`에 React(Vite) 프로젝트를 만들고 화면 테스트 도구(Vitest, Testing Library)를 준비합니다.
5. 첫 화면에서 서버의 상태 확인 주소를 불러와 "서버와 연결됨"을 보여줍니다.
6. 서버가 화면 주소(`http://localhost:5173`)의 요청만 받도록 허용 목록(CORS)을 설정합니다.
7. SQLite 파일 경로를 `database/buildlog.sqlite3`로 정하되, 이 Phase에서는 데이터베이스를 만들지 않습니다.
8. 비밀값은 환경 변수(`.env`)에서 읽도록 하고 `.env.example`에는 항목 이름만 기록합니다.
9. SQLite 파일, 테스트 캐시와 개발 중 생성되는 파일을 `.gitignore`에 보완합니다.
10. 서버와 화면의 빈 테스트가 각각 통과하는지 확인합니다.

#### 예상 변경 파일

- `backend/requirements.txt`
- `backend/.env.example`
- `backend/app/main.py`
- `backend/app/config.py`
- `backend/tests/test_health.py`
- `frontend/package.json`
- `frontend/.env.example`
- `frontend/src/` 아래 기본 화면과 서버 요청 코드
- `.gitignore`

#### 확인 방법

- 서버가 오류 없이 시작되고 상태 확인 주소가 열리는지 확인합니다.
- 브라우저에서 첫 화면이 보이고 "서버와 연결됨"이 표시되는지 확인합니다.
- 화면 주소가 아닌 곳에서 온 요청은 서버가 받지 않는지 확인합니다.
- 서버 테스트와 화면 테스트 명령이 오류 없이 끝나는지 확인합니다.
- 비밀 설정값과 SQLite 파일이 Git 기록 대상에서 제외되는지 확인합니다.

#### 완료 조건

- 서버와 화면이 정상 실행되고 서로 연결되어야 합니다.
- 사용자 데이터 구조를 만들기 전에는 데이터베이스 마이그레이션을 실행하지 않습니다.

---

### Phase 2. 사용자 데이터 구조와 첫 데이터베이스 만들기

#### 목표

이메일로 로그인하는 사용자 구조를 가장 먼저 확정하고 첫 데이터베이스를 만듭니다.

#### 작업

1. 데이터 접근 도구(SQLAlchemy)와 마이그레이션 도구(Alembic), 비밀번호 보호 도구를 설치하고 `requirements.txt`에 기록합니다.
2. 서버의 데이터베이스 연결(`database.py`)을 만들고, 연결 주소를 `.env`의 `DATABASE_URL`에서 읽게 합니다. 개발 기본값은 SQLite 파일입니다.
3. `accounts` 안에 사용자 데이터 구조를 만듭니다: 이메일, 안전하게 처리한 비밀번호, 닉네임, 운영자 여부, 가입 날짜·시간.
4. 이메일은 필수이며 중복되지 않게 합니다.
5. 닉네임은 필수이며 중복되지 않게 합니다.
6. 닉네임은 2~20자이고 한글, 영문, 숫자, 밑줄만 허용합니다.
7. 비밀번호는 원문이 아닌 안전하게 처리한 값만 저장합니다. 비밀번호 원문은 어디에도 저장하거나 기록하지 않습니다.
8. 운영자 여부의 기본값은 "아님"입니다. 운영자 지정은 데이터베이스에서 직접 하며 화면에서 운영자를 만드는 기능은 없습니다.
9. 첫 마이그레이션을 만들고 빈 SQLite 데이터베이스에 적용합니다.
10. 자동 테스트는 매번 새로 만든 임시 SQLite 데이터베이스에서 실행되게 합니다.
11. 사용자 데이터 구조 단위 테스트를 작성합니다.

#### 예상 변경 파일

- `backend/requirements.txt`
- `backend/.env.example`
- `backend/app/database.py`
- `backend/app/security.py`
- `backend/app/accounts/models.py`
- `backend/app/accounts/schemas.py`
- `backend/alembic/`
- `backend/tests/test_users.py`
- `database/buildlog.sqlite3` (Git 제외)

#### 확인 방법

- 서로 다른 이메일과 닉네임으로 사용자를 저장할 수 있는지 확인합니다.
- 같은 이메일이나 닉네임을 중복 저장할 수 없는지 확인합니다.
- 닉네임 길이와 허용 문자 검사가 동작하는지 확인합니다.
- 비밀번호 원문이 데이터베이스에 저장되지 않는지 확인합니다.
- 서버를 종료하고 다시 시작해도 사용자 데이터가 남아 있는지 확인합니다.
- 자동 테스트가 실제 개발용 데이터 파일을 건드리지 않는지 확인합니다.

#### 완료 조건

- 첫 마이그레이션과 사용자 테스트가 모두 통과해야 합니다.
- 사용자 구조를 다시 바꾸기 위해 데이터베이스를 지워야 하는 문제가 없어야 합니다.

### Phase 3. 회원가입·로그인·닉네임 변경

#### 목표

사용자가 계정을 만들고 로그인한 뒤 자신의 닉네임을 바꿀 수 있게 합니다.

#### 작업

**서버**

1. 회원가입 요청을 받아 이메일·닉네임의 앞뒤 공백을 제거하고, 이메일 형식, 중복 이메일, 중복 닉네임, 비밀번호 8~64자, 닉네임 조건을 검사합니다.
2. 로그인 요청을 받아 이메일과 비밀번호가 맞으면 로그인 확인 값(토큰)을 줍니다. 틀리면 "로그인 정보가 맞지 않다"고 알립니다.
3. 로그인한 사용자를 확인하는 공통 기능을 만들고, 로그인하지 않은 요청은 기록 관련 요청을 거절합니다.
4. 닉네임 변경 요청을 만들고, 로그인한 본인만 가능하게 합니다.

**화면**

5. 회원가입 화면을 만들고, 실패 시 이메일과 닉네임은 유지하고 비밀번호만 지웁니다. 성공하면 로그인 화면으로 이동합니다.
6. 로그인 화면을 만들고, 실패 시 이메일은 유지하고 비밀번호만 지웁니다. 성공하면 내 기록 홈 화면으로 이동합니다.
7. 로그인 확인 값은 브라우저에 보관하고, 로그아웃하면 지웁니다. 로그인 상태는 로그아웃할 때까지 유지합니다.
8. 로그인하지 않은 사용자가 기록 화면에 접근하면 로그인 화면으로 보냅니다.
9. 계정 설정에서 닉네임을 변경하게 합니다. 실패하면 이유를 알려주고 입력한 닉네임을 유지합니다.
10. 공통 화면 틀(위쪽 메뉴, 계정 설정, 로그아웃)을 만듭니다. 로그인·가입 화면에는 메뉴를 보여주지 않습니다.
11. 공개 기록과 댓글에서 사용자의 현재 닉네임을 읽도록 준비합니다.

**정한 세부 사항** (`spec.md`에 직접 적혀 있지 않아 계획에서 정함)

- 로그인 상태 유지와 로그아웃 버튼은 위 내용으로 합니다. 바꾸고 싶으면 알려 주세요.

- 본인 기록·댓글을 신고할 수 있는지는 `spec.md`에 없습니다. 지금은 막지 않고 `spec.md`대로 만듭니다.

### Phase 14. Supabase 연결과 인터넷에 올리기

#### 목표

3. 서버의 전체 자동 테스트를 Supabase(테스트용 프로젝트)에서도 실행해 SQLite3와 같은 결과인지 확인합니다.
4. 브라우저가 Supabase에 직접 접근하지 못하도록 보호 설정을 하고, 서버만 접근하게 합니다.
5. 서버와 화면을 각각 어디에 올릴지 정합니다. (**미정**: 이 Phase 시작 전에 선택지, 비용, 난이도를 설명하고 함께 정합니다.)
6. 실제 서비스용 설정으로 바꿉니다. 비밀값은 올리는 곳의 설정에만 넣고 코드에는 넣지 않습니다.
7. 서버가 올라간 화면 주소의 요청만 받도록 허용 목록(CORS)을 바꿉니다.
8. 운영자 계정을 지정합니다.
9. 백업 방법을 정합니다.
10. 폰과 다른 컴퓨터에서 가입, 기록 작성, 공개, 댓글, 좋아요, 신고까지 확인합니다.

#### 확인 방법

- Supabase에서 마이그레이션과 자동 테스트가 모두 통과하는지 확인합니다.
- 인터넷 주소로 접속할 수 있는지 확인합니다.
- 폰에서 쓴 기록이 다른 컴퓨터에서도 같은 계정으로 보이는지 확인합니다.
- 서버를 다시 시작해도 기록이 남아 있는지 확인합니다.
- 로그인하지 않고는 어떤 기록도 볼 수 없는지 확인합니다.

#### 완료 조건

- Supabase에서도 `spec.md`의 확인 항목이 통과해야 합니다.
- 인터넷 주소로 폰과 다른 컴퓨터에서 접속할 수 있어야 합니다.

## 7. 실제 진행 방법

1. 첫 작업은 Phase 0만 진행합니다.
2. Phase 0의 결과와 확인 내용을 공유합니다.
3. 사용자가 확인하면 Phase 1만 진행합니다.
4. 이후에도 같은 방식으로 Phase 하나씩 진행합니다.
5. 여러 Phase를 한 번에 구현하지 않습니다.
